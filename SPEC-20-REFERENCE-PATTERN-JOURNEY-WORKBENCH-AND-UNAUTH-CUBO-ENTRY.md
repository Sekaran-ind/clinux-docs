# Specification 20: Reference-Pattern Journey Workbench, Applied First to Unauthenticated Cübo Entry

## 1. Objective

Formalize a concrete reference pattern the user shared (a working single-file "Agentic CPQ Workbench" demo — Alpine.js, TanStack Store, Observable Plot, Leaflet/OSM, a versioned product catalog, 5 "Copilots") against SPEC-15/16's still-abstract three-pane design, then apply it to the smallest real, already-buildable target: Cübo's unauthenticated entry point on Index.vue, hosting Register/Login/Change-Password/Forgot-Password as a Task-driven journey in a "General" thread. Nothing here is built yet except what SPEC-13's auth closed loop already shipped (§3).

## 2. What the reference demo actually shows, mapped to real ClinuxFlow equivalents

Read directly from the shared screenshots, not summarized from memory:

- **§2.1 Journey picker (bounded-context entry).** A "Choose a product journey" landing screen: one card per product (GSIP/ICG-ICR/IPCG2), each showing a short description, metadata chips ("9 HFSM steps", "1 location(s)"), a **catalog version** selector, and a "Start journey with vX.0" CTA. This is SPEC-12's Rooms concept and SPEC-16's notebook-anchor concept, made concrete as a real landing UI — ClinuxFlow doesn't have an equivalent picker screen anywhere yet (Front Desk/Consultation Desk/Checkout are reached via ClinicHome's internal view-switching, not a bounded-context picker; the auth loop has no picker at all, it's just Index.vue's existing register/login modals).
- **§2.2 Left pane: a real numbered stepper, not a flat list.** Five numbered steps grouped by phase (QUALIFY ①②③ / CONFIGURE ④ / PRICE ⑤), each tagged with the real **TM Forum Open API resource type** behind it (TMF632 Party, TMF674 Geographic Site, TMF679 Qualification, TMF620 Product Catalog, TMF648 Quote), current step highlighted, a "Quote readiness 13%" completion bar above it. This is a genuine implementation of SPEC-16 §5's "Task hierarchy nested within each notebook, node status shown inline" — and it only works because the CPQ demo has a real, fully-modeled Task graph behind every step. **This is exactly why AI Engine's left pane (SPEC-19 §12 step 2.1) had to stay a flat category list** — it has no PlanDefinition backing it. The auth journey (§3 below) is the first ClinuxFlow surface that *can* get this real stepper, because `AUTH_PLAN_DEFINITION` already exists.
- **§2.3 Middle pane: inline data capture, not a drawer.** "Who is this quote for?" renders its `Customer / account name` / `Primary contact email` inputs directly in the conversational flow — confirms SPEC-15 §5/§6's "structured data renders as cards interleaved with the narrative... one card per section," now with a concrete worked example rather than an abstract description. A visually distinct **"Sales Copilot" card** (icon, name, one-line disclosure of what it does and doesn't do: "*converts customer intent into a candidate configuration — never commits it for you*") sits alongside the plain fields, with its own mini-textarea and its own action button ("Ask Sales Copilot for a starting configuration"), returning a concrete suggested value the user must explicitly apply — this is the right shape for a genuine Copilot-suggests/human-confirms interaction, sharper than anything currently in `Cubo.vue` (whose only "AI" today is a single hardcoded canned reply, per the AI Engine work this session).
- **§2.4 Right pane, tabbed — Map / TMF / Copilots / **Observe** / **Audit**.**
  - *Entity view*: a header summary (id/state/customer/price-style key fields) plus a **live raw JSON viewer** of the actual underlying entity being built — the CPQ demo's `Quote` resource. ClinuxFlow's equivalent for the auth journey isn't a FHIR resource at all (accounts are a plain D1 table, not FHIR-typed) — worth being honest about rather than forcing a FHIR label onto something that isn't one; §3 below names the real shape.
  - *Observe*: "Reactive journey telemetry" — an Observable-Plot bar chart of per-stage completeness, plus two metric tiles (`HFSM EVENTS: 3`, `BLOCKED ATTEMPTS: 1`). **Nothing like this exists anywhere in ClinuxFlow** — `planDefinitionRunner.js`/`workflowRuntime.js` compile and route Task state but never accumulate an event/telemetry log a UI could chart.
  - *Audit*: a real, structured, three-part log — (a) HFSM transition history (`QUALIFY.customer → QUALIFY.locations`, timestamped), (b) Copilot interactions logged *separately* from transitions ("Sales Copilot — Suggested", "Qualification Copilot — Explained", each timestamped with its content), (c) blocked/invalid attempts (a validation failure that never became a transition, still logged). **Also doesn't exist anywhere in ClinuxFlow.** This is a real, well-specified gap worth naming precisely rather than folding vaguely into "add logging later."
  - A footer disclosure line, verbatim in two screenshots: *"Guided controls only — this session is persisted solely in this browser via localStorage. Map/geocoding calls go only to the public OpenStreetMap Nominatim service, never to a CPQ backend."* — an explicit, user-facing data-scope disclosure baked into the UI itself, not just a code comment. Worth adopting as a pattern: every guided journey should say, in the UI, where its data actually goes.
- **§2.5 Conditional repeating groups, inline.** The site-capture step's "+ Add another site" is visibly gated by a stated business rule shown right next to it ("*Add a second site only if Secure+ Split resilience is expected — otherwise one primary site is enough*") — `enableWhen`/`skipLogic` made visible as a plain-language reason, not just a hidden conditional. Real map validation (Leaflet + OSM Nominatim) with an explicit offline/manual-confirm fallback sits alongside it.

## 3. First application: unauthenticated Cübo entry on Index.vue

Direct instruction: *"In unauthenticated Cübo context it should enter in General category Thread, Registration, Login, change password, forgot password journeys could be facilitated as state machine (already built) in the general thread. basically index page user options."*

This is the smallest real target because almost everything it needs already exists and is tested:

- **The HFSM is real and already built**: `AUTH_PLAN_DEFINITION` (`clinux-frontend/src/workflow/authPlanDefinition.js`) — `register → login → change_password`, `relatedAction`-gated, validated end-to-end through the real runtime this session (`clinux-planDefinition-runtime-built` memory). `register`/`login` already call real routes; `change_password` already has a real backend (`PATCH /api/auth/change-password`, built this session specifically for this loop).
- **What's genuinely missing**:
  1. **Forgot Password** — not in `AUTH_PLAN_DEFINITION` at all. Needs a real backend (a token-based reset flow — no email-sending infrastructure exists anywhere in this app yet, same gap Phase D's team-invite flow already documented working around: *"No mail server exists in this app... the inviting admin sets the new teammate's email+password directly... shares it out of band"* — forgot-password can't reuse that shortcut, since the whole point is the user has lost their password and can't be handed a new one out-of-band by themselves). This needs a real design decision before building, not a guess.
  2. **A "General" Cübo thread that hosts these four as journey options**, replacing or sitting alongside Index.vue's existing register/login modals — not decided yet whether additive (a new "Try guided setup" entry point, matching the precedent `HospitalOnboarding.vue`'s "Try the chat-based setup" card set for SPEC-14) or a replacement.
  3. **The left-pane stepper wired to real `AUTH_PLAN_DEFINITION` state** (`actionStatus`/`readyActionIds` selectors already exist, per §2.2 — this is the one piece of the reference pattern that transfers with a real, honest Task graph behind it, not a flat-list compromise).
  4. **Inline data capture in the middle pane** (§2.3) — email/password fields rendered in the conversational flow itself rather than a modal, `register`'s payload built the same way the "Who is this quote for?" card built its.
  5. **Observe/Audit tabs (§2.4)** — real net-new work, nothing to adapt from. Scope decision needed: build a real event log now (a new, small addition to `workflowRuntime.js` — `actor.subscribe()` already fires on every transition, so accumulating a timestamped log is a small, well-understood addition to something already working) versus deferring telemetry/audit until after the interaction shell itself is proven.

## 4. Scope decisions

1. **Additive** — the new Cübo-hosted flow is a new entry point alongside Index.vue's existing register/login modals (same precedent as `HospitalOnboarding.vue`'s "Try the chat-based setup" card, SPEC-14 §7), not a replacement. Nothing existing can regress.
2. **Forgot Password: security-question recovery, no email infrastructure.** A security question + answer captured at registration (hashed the same way `passwordHash.js` already hashes passwords), verified to allow a password reset — works for a solo admin with no one above them to reset it, not just team accounts.
3. **Audit now, Observe deferred.** `workflowRuntime.js` already calls `actor.subscribe()` on every transition (built this session for persistence) — a timestamped transition/copilot-interaction log is a small, real addition on top of that, not new machinery. The Observable-Plot completeness chart (§2.4) is deferred — genuinely new surface with nothing to attach to yet.
4. **A real structural gap found while designing this, not hypothetical**: `AUTH_PLAN_DEFINITION`'s `login` depends on `register` reaching `done` (`relatedAction`) — correct for validating the runtime's sequencing mechanics in a closed-loop test (SPEC-13 §9), **wrong for the real entry point** — a returning user must be able to log in without re-registering first. A distinct, real entry PlanDefinition is needed (§3 below), not a reuse of the test-validation one unchanged. `change_password`'s real gate is "the caller is currently authenticated," which `PATCH /api/auth/change-password`'s `requireUser()` middleware already enforces server-side regardless of what the client-side graph declares — so the new entry PlanDefinition leaves `change_password` structurally un-gated (no `relatedAction`) rather than inventing OR-dependency support `planDefinitionRunner.js` doesn't have; correctness comes from the real backend check, same as it already does today.

## 5. Built and live-verified (backend + runtime — unchanged by §6's UI correction)

- **Backend** (`clinuxflow-api`): `migrations/0009_add_security_question.sql` (nullable `security_question`/`security_answer_hash` on `accounts`), `AccountsDb.updateSecurityQuestion`, and three real routes — `PATCH /api/auth/security-question`, `POST /api/auth/forgot-password/question`, `POST /api/auth/forgot-password/reset` — all reusing `passwordHash.js`'s existing PBKDF2 scheme for the security answer (normalized trim+lowercase, so "Blue"/"blue "/" BLUE" all match). 11 new tests, 182/182 total.
- **Runtime** (`clinux-frontend`): `src/workflow/entryPlanDefinition.js` (`ENTRY_PLAN_DEFINITION` — register/login/forgot_password/change_password, all four structurally ungated, per §4 point 4) + `buildEntryServices`. `workflowRuntime.js` gained a real `auditLog` (transition + blocked-attempt entries, diffed off each snapshot) — additive on top of the existing `actor.subscribe()` persistence hook, no new machinery. `src/stores/entryWorkflow.js` (new, added in §6's rework) is this runtime's real app-wide home — a Pinia store, not a page-local instance.

**Deliberately not built**: the Observable-Plot-style Observe tab (completeness chart, event-count tiles) and the "Copilot interactions" audit category (nothing real generates such an event yet — see `workflowRuntime.js`'s own comment on why). §4 point 3's Audit log is instead surfaced as narrated Cübo chat messages (§6), not a dedicated log pane — there's no pane to put one in once this isn't a standalone 3-pane page.

## 6. Correction: hosted directly in Cübo's General thread, not a standalone page

**The first built version of §5's UI was wrong**, per direct correction: *"GetStartedVue is a thread instance in C[ü]bo for Gene[r]al Category, we should not have a se[p]arate vue page for it. We have Gene[r]al Category, Encounter Category threads already in Cubo."* This was a real miss — SPEC-15 §1 already states *"Cübo hosts guided-flow capture directly rather than a standalone page,"* and `stores/cubo.js` already had `general` as a first-class category (*"a persistent session channel, not a scoped workspace tied to one record"*) with `activeThreadId` defaulting to it — infrastructure the first version ignored in favor of a new, parallel one. `src/pages/GetStarted.vue` and its `/get-started` route are deleted.

**Corrected architecture**:
- **Shared, host-agnostic form components** (`src/components/auth/{Register,Login,ForgotPassword,ChangePassword,SecurityQuestion}Form.vue`) — no opinion about being in a modal or inline in a chat message. `Index.vue`'s existing register/login modals now render these same components instead of their own duplicated markup; `Cubo.vue` renders them inline. One implementation, two hosts — closes the exact duplication risk flagged when this session first proposed the split.
- **Rich-content chat messages**: `chatThreads.js` messages gained optional `component`/`componentProps` fields; `Cubo.vue`'s render loop mounts a real Vue component (via `<component :is>`) for a message that carries one, in a wider card block separate from the narrow text-bubble styling. Resolved a real open design question (asked directly: size-adaptive-with-a-pop-out-affordance, vs. every form always being a button) as **size-adaptive, explicit-per-component** — all four auth forms are small enough to declare themselves inline-eligible for now; a future large/repeating-group form would render a summary card + pop-out button instead, reusing SPEC-15 §4's existing "dense content pops out" rule rather than inventing a second mechanism. No form in this pass needed to exercise the pop-out path.
- **Entry menu**: `Cubo.vue`'s `onMounted` now seeds the General thread with an assistant message + 4 quick-action buttons (Register/Login/Forgot Password/Change Password) the first time an unauthenticated visitor reaches it; picking one appends the matching inline form. A successful register appends the `SecurityQuestionForm` as a follow-up message in the same thread (skippable); every transition is narrated as a plain chat message rather than surfaced in a separate log pane.
- **Index.vue** didn't mount `<Cubo>` at all before this — now does (default FAB). The former "Try Guided Setup with Cübo" link (which pointed at the deleted route) now just expands Cübo directly (`cubo.currentLayout = 'EXPANDED'`).

**A real bug found and fixed via live testing, not a hypothetical**: `RegisterForm`/`LoginForm`/etc. can be mounted more than once simultaneously — Index.vue's modal keeps its instance mounted (`v-show`, not `v-if`) even while hidden, and Cübo's thread renders a second, independent instance. `entryWorkflow.js`'s `statuses`/`errors` are real shared Pinia state (the whole point of Task-tracking), so a naive `watch(() => statuses.register, ...)` fired on **every** mounted instance whenever **any** instance's submission succeeded. Caught live: submitting Cübo's inline register form also triggered the hidden modal's stale success handler, which navigated the whole page to `/clinic-home` mid-conversation. Fixed with a per-instance `submitting` flag — a form only reacts to a status transition it caused itself, checked before every one of its four form components' `watch` callbacks now.

**Also found and fixed**: `entryWorkflow.js`'s `ensureStarted()` subscribed to the actor *after* `workflowRuntime.js`'s `registerPlan()` had already called `actor.start()` internally — a late subscriber never gets XState's already-fired initial-snapshot notification replayed, so `statuses`/`errors` silently stayed `undefined` (not `'ready'`) until the *next* real transition. Caught by a genuinely failing unit test, not observed live (the UI's own `|| 'pending'` fallback in the earlier standalone-page version happened to render a plausible-looking, merely-wrong status dot). Fixed by calling `refresh()` once manually right after subscribing.

**Live end-to-end verified against the real backend** (not the old page, the real `Cubo.vue`-hosted flow): opened Cübo from Index.vue's new button → entry menu appeared → Register rendered inline, submitted → **stayed on Index.vue** (confirms the multi-instance fix) → security-question card appeared in the same thread → saved → confirmation message. Separately, a fresh session (cleared localStorage) → Log In via the same General thread → succeeded → Index.vue's own header reactively updated (avatar, clinic name) with zero page navigation, proving `auth.currentUser` flows correctly out of the Cübo-hosted flow into the rest of the page. Zero real console errors throughout (only the pre-existing, expected LAN-shared-server health-probe noise).

## 6.1 Completed-state collapse + confirmed-pending thread-routing scope

Two follow-up reports after §6 shipped, both resolved:

1. **A completed form kept showing as a live, empty, resubmittable form** — real gap, fixed. Each rich-content message now carries its own `done`/`doneLabel` fields (`Cubo.vue`'s `markMessageDone`), set by the specific form instance's own success/skip handler. Deliberately **per-message**, not a read of `entryWorkflow`'s shared global status — `change_password` can legitimately be submitted more than once in a session, and a global-status read would incorrectly flip an unrelated older message's display too. Once done, the message renders a compact "✓ Registered"/"✓ Signed in"/"✓ Skipped"/etc. chip instead of the live form. Live-verified: register → chip reads "Registered"; skip the security-question follow-up → chip reads "Skipped" (not, as first shipped, the wrong hardcoded "Recovery question saved" for the skip path too — caught and fixed in the same pass).
2. **"AI Engine's Cübo and Index's Cübo don't show the same thread info."** Tested directly rather than assumed: registered + sent a message in the General thread on Index.vue, did a *real* SPA navigation (`router.push`, not a reload) to AI Engine, opened the Threads list from AI Engine's own Cübo instance — **both threads showed up fully, correctly, with the right content**. The underlying data (`chatThreads` collection, the `cubo` Pinia store) is genuinely shared and consistent; nothing is lost or diverges. What actually differs is *which thread displays by default* — `<Cubo category="ai-engine">` auto-switches the active thread on mount, exactly the same pre-existing mechanism Front Desk/Checkout/Consultation Desk/Billing/ABDM already rely on for legitimate per-encounter/per-patient conversation isolation (predates this session entirely). **Confirmed as already-correctly-scoped pending design, not a gap**: SPEC-16 §5's own text — *"reusing `chatThreads.js`'s existing `category` field's role, now backed by real anchor-id/notebook identity rather than a label string"* — is precisely the fix (category routing driven by the real running Task/PlanDefinition state, not a static prop), and SPEC-16 §6 step 1 already names its blocking prerequisite (`Task`/`PlanDefinition` persistence, still open) and SPEC-15 §10 already names the open item ("exact `Cubo.vue` integration point for hosting an HFSM-driven thread — not yet designed"). Decision: leave the current category-prop mechanism untouched rather than build an interim patch that would just be thrown away once SPEC-16's real Task-anchor routing lands.

## 6.2 A third real bug: `done` was permanently terminal, breaking any repeat action

Reported directly: *"i cannot login now.. no error is shown."* Reproduced live rather than guessed at — a *second* login attempt in the same session (log out, then log in again) silently did nothing: no API call, no error, nothing. Root cause in `planDefinitionRunner.js`: every action's `done` state was hardcoded `type: 'final'` — an XState terminal state that never accepts another event, ever. Correct for `register` (genuinely one-shot, an email registers once), **wrong for `login`/`forgot_password`/`change_password`**, all of which a user can legitimately need to redo in one session. A second `FOCUS` on an already-`done`, `final` region is simply dropped by XState with no signal at all — exactly the "no error is shown" symptom reported.

**Fixed with an explicit, opt-in `action.repeatable` flag** (not a blanket behavior change to every action, which would incorrectly let `register` be re-triggered too): a repeatable action's `done` state gets its own `FOCUS` handler back into `active` — reusing the exact same invoke/error-clearing logic `active` already has — instead of `type: 'final'`. `login`/`forgot_password`/`change_password` in `ENTRY_PLAN_DEFINITION` are now marked `repeatable: true`; `register` is unchanged (still one-shot). Every other existing `PlanDefinition` (the 5-room clinical draft, `AUTH_PLAN_DEFINITION`) is unaffected — the flag defaults to falsy, preserving `type: 'final'` exactly as before. 2 new tests in `planDefinitionRunner.test.js` (one reproducing the bug directly against a non-repeatable action, one proving the fix against a repeatable one) + 1 new integration test in `entryPlanDefinition.test.js` (a real second `login` FOCUS through the actual runtime). Live-verified: reproduced the exact silent-failure via Playwright first (confirmed `authStore.login`/the real API were never called a second time), then confirmed fixed the same way (second `/api/auth/login` call fires, `200`, authenticated).
