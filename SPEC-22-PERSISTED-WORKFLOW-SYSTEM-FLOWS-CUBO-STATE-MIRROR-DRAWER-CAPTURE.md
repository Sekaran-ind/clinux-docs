# Specification 22: Four Foundational Decisions — Persisted Workflow, System-Flows, Cübo State-Mirroring, Drawer-Based Capture

## 1. Objective

Lock in four architectural decisions as durable, not exploratory: (1) Task/PlanDefinition/Event resources persist and are viewable like any other clinical entity, feeding a personal worklist on login; (2) a `system-flow` YAML library, parallel to system forms; (3) Cübo's active thread mirrors the application's own auth/journey state, including a hard reset on logout; (4) all form-shaped data capture through Cübo opens a drawer, never renders inline — route navigation is always an explicit action, never silent. **Decision 4 directly corrects part of `docs/SPEC-20-REFERENCE-PATTERN-JOURNEY-WORKBENCH-AND-UNAUTH-CUBO-ENTRY.md` §6's shipped inline-form rendering** — stated plainly in §5, not glossed over. Nothing in this spec is built yet except what's noted as already-real.

## 2. Decision 1: persisted Workflow/Request/Event resources + a personal worklist

*"The workflow, request and event resources should be persisted like encounter and provider entities in other journeys. The plan definition, task, current status etc can be viewed. This should be used in navigations when user logs back in with his confirmation — maybe like a personal worklist."*

**What's real today, checked directly, and why it's not the same thing**: `src/data/collections/taskActorSnapshots.js` persists — but it stores `actor.getPersistedSnapshot()`, an opaque, XState-internal serialized blob, not a real, independently-shaped FHIR resource the way `formData.js`/`encounterDocs.js` store real `QuestionnaireResponse`-shaped records for Encounter/Provider entities. You cannot query "what Tasks does this user have open" against a snapshot blob without deserializing it back through XState first. This is exactly the gap `docs/SPEC-16-NOTEBOOKS-AND-TASK-PRIMARY-NAVIGATION.md` §6 step 1 already named as blocking: *"no `Task`/`PlanDefinition` resource is persisted anywhere yet... Task persistence itself remains open."* This decision is that gap, now committed to, not a new idea.

**What this requires, precisely**:
- A real `taskRecords` collection (or similar), one row per Task instance, shaped as an actual FHIR-ish `Task` (id, `status` — using the real 12-code mapping SPEC-19 §9 already worked out for `pending/ready/active/done`, not reinvented — `focus`/`for` references, `lastModified`), separate from the XState snapshot (which still needs to exist for actually *running* the machine — the two aren't a replacement for each other, they're complementary: the snapshot resumes execution, the Task record is what's browsable).
- A worklist UI — "here's what you have open" — shown at login, **with explicit confirmation before navigating**, not silent auto-resume. Ties directly into decision 3's login-time thread-switching and SPEC-21 §5's already-built role-based suggestion (this becomes richer than a static per-role suggestion once real open Tasks exist to list).
- Genuinely the largest of the four decisions — a real data-modeling exercise plus a new UI, not a small addition.

## 3. Decision 2: `system-flow` YAML library, parallel to system forms

*"Like system forms, there should be a system-flow that should be configurable in yaml with conditions, steps and guards."*

**Already designed, largely already built at the compiler level — the gap is the library + runtime connection, not the compiler.** `docs/SPEC-18-PLANDEFINITION-AUTHORING-VIA-YAML-PIPELINE.md` is precisely this: a `workflow-definition.yaml` compiled through the same `yaml-to-questionnaire.js`/`local-extractor.js` pipeline `system-forms-library.json` already uses, action id/title/`relatedAction`/condition all real, nested-group support, the condition-type `ValueSet` (extended in SPEC-21 §5 with `role-equals`) all real and tested (166/166 clean at the time, since grown).

**What's still genuinely missing**: (a) a real *library* of authored system-flow YAML files, analogous to `formsLibrary.js`/`seedSystemForms` — today only one draft (`workflow-definition-v1.draft.yaml`) exists, and it's a test fixture, not a seeded, selectable library entry; (b) a loader/registry mirroring `formsLibrary.js`'s pattern; (c) the actual connection from a *compiled* PlanDefinition to `planDefinitionRunner.js`/`workflowRuntime.js` — today `entryPlanDefinition.js`/`authPlanDefinition.js` are hand-authored JS objects, and the runtime has never once consumed a YAML-compiled PlanDefinition for real. Closing (c) is the real, concrete missing link between SPEC-18's compiler and SPEC-13's runtime.

**UPDATE — first real (non-draft) system-flow YAML authored and compiler-verified**: `clinuxflow-api/samples/hospital-setup-workflow-v1.yaml`, sequencing the 4 real Hospital-related `composition` blocks of `tools/system-forms/system-provider-composition-v1.yaml` (`section_hospital` → `section_hospital_abdm_facility_type` → `section_hospital_abdm_location` → `section_hospital_abdm_registration`, linear, each `relatedAction`-dependent on the previous via `after-end`) as `PlanDefinition.action` entries. Deliberately does **not** redeclare those sections' fields — action ids are set equal to the real section linkIds, and the intended (not-yet-built) runtime resolves "current action = section_hospital" by slicing that one group out of the already-compiled Provider Questionnaire and rendering it alone, reusing two real, already-tested primitives unmodified: `useSystemForms.js#extractResponse` (read a rendered LForms container back out as a QuestionnaireResponse) and `formData.js#withGroupFields` (merge one group's fields into the existing Provider record without touching the others). Two sources of truth for the same fields was the alternative rejected here. Scope deliberately Hospital-only — Provider/Staff/Services/Hours/Consent/Appointment are a separate, later system-flow, matching the user's own stated order ("hospital setup, provider setup").

**Real compiler-level bug found and fixed along the way**: `clinuxflow-api/src/lib/local-extractor.js`'s `groupInstanceCounters` keyed a nested repeating group's instance index (e.g. `relatedAction` under `action`) by the group's own `linkId` alone, globally across the whole response — not scoped to which parent instance it belonged to. `workflow-definition-v1.draft.yaml`'s 2-room fixture never caught this (only one room had a populated `relatedAction`, so a global count and a per-parent count coincided). This YAML's realistic 4-step linear chain (3 of 4 steps each contributing their own single `relatedAction`) exposed it directly: steps 3 and 4 wrote into `relatedAction[1]`/`relatedAction[2]` of their own array instead of `[0]`, leaving `undefined` holes at the front. Fixed by keying the counter on the full enclosing-frame path (each frame's own `linkId:instanceIndex`) plus the child's own linkId, not the linkId alone — makes each parent instance's nested count independent, matching the extractor's own stated "genuinely nested... frame per enclosing group" design intent that the counter just hadn't followed through on. New test (`hospital-setup-workflow.test.js`) added as the regression case; `workflow-definition-draft.test.js` still passes unchanged. 186/186 clinuxflow-api suite clean.

## 4. Decision 3: Cübo mirrors the application's own state

*"Cübo should follow and reflect the same state as the application... when I logout the application, Cübo should reset to begin a new general thread. Cübo... can be on Unauthenticated state when only General thread is active. In Authenticated and in Hospital state then Administration thread to be active and in Authenticated and in Encounter state then Encounter thread to be active."*

**Checked against real code — two of three cases already work, one doesn't, one doesn't exist yet:**
- **Unauthenticated → General only**: already true (SPEC-20) — nothing else is reachable before authentication.
- **Authenticated + Encounter → Encounter thread**: already real and correct — `Cubo.vue`'s existing `encounterId` prop routing (`createNewThread('encounter', ...)`), unchanged, no gap.
- **Authenticated + Hospital → Administration thread**: **doesn't exist.** `CUBO_CATEGORIES` (checked directly) has no `administration` entry — the closest existing categories (`front-desk`, `billing`, `ai-engine`, `abdm-facility`) don't cover "Hospital state" as a whole. A new category is needed, and "Hospital state" itself needs a precise definition — read as covering ClinicHome/Designer's Forms Library/HospitalOnboarding/StaffOnboarding/AbdmOnboarding as one shared administration thread, not one thread per page.
- **Logout doesn't reset Cübo at all** — real gap, checked directly: `auth.js`'s `logout()` only clears `currentUser`/the session token; it never touches `cubo.activeThreadId` or the thread itself. A user could log out and still see an Authenticated-only thread (or, worse, a stale "Signed in" chip) on a page a signed-out visitor shouldn't be looking at.

**This is the concrete first real piece of a Task-primary/notebook-anchor left pane** (SPEC-16's own eventual design) — not the full notebook model yet, just the state-driven thread-selection rule underneath it: `authStage × journeyContext → activeThreadCategory`, computed centrally rather than left to each page's own static `category` prop.

## 5. Decision 4: drawer-based capture, action-based navigation — corrects SPEC-20 §6

*"All lhcforms should be captured in the drawer panel instead of inline components. Route navigations should be presented as an action in Cübo for user to take action."*

**Second half already correct, ship as-is**: SPEC-21 §5's `nav-suggestion` messages are exactly this — a real button, the user takes the action, nothing silent. No change needed.

**First half is a real, explicit correction, stated directly rather than minimized**: SPEC-20 §6 built `RegisterForm`/`LoginForm`/`ForgotPasswordForm`/`ChangePasswordForm`/`SecurityQuestionForm` rendering **inline** in Cübo's message stream — the "small forms render inline, only large ones pop out" design this session settled on two exchanges before SPEC-20 shipped. This decision reverses that: **all** form-shaped capture opens a drawer, uniformly, regardless of size. Worth being honest about rather than quietly walking back: the earlier size-adaptive call is superseded, not refined.

**A real scoping gap to close before building, checked directly**: there is no generic, reusable Drawer component anywhere in this codebase — every page (`HospitalOnboarding.vue`, `Designer.vue`, `Onboarding.vue`, ...) has its own bespoke `.drawer-backdrop`/`.drawer-panel` markup and local open-state, sharing only global CSS class names. "Cübo opens a drawer" therefore means one of two real choices, not an already-solved mechanism: (a) build a genuine shared `Drawer.vue` component Cübo mounts on demand, hosting whichever form is relevant; or (b) have Cübo trigger each *target page's own* existing drawer state (less general, more reuse of what already works per page). Needs a real decision, not assumed — (a) is more consistent with "Cübo is the one dispatcher," (b) is less new code. The five SPEC-20 auth forms would move into whichever shape is chosen.

## 5.1 Refinement: not drawer-vs-inline — the standing 3-pane shell, responsive by width

This reframes §5 precisely: it was never drawer-vs-inline as an either/or architectural rule. It's that a real third pane (structured data/capture, distinct from the conversation) needs to **exist as a standing part of Cübo's own layout**, and whether it renders as a persistent column or collapses behind a toggle is a **responsive width concern**, not a fixed choice per feature.

**A real, already-shipped precedent covers exactly this, found directly rather than invented fresh**: `.chat-forms-shell` / `.chat-pane` / `.content-pane` / `mobileView` ref / `.mobile-toggle-fab`, `@media (max-width: 768px)` (`src/style.css`, documented there as replacing the original PR #7) — Front Desk, Consultation Desk, and Checkout already do precisely "Cübo pane + content pane side by side above 768px, toggle below it." SPEC-20 §6's mistake wasn't choosing inline over a drawer — it was rendering the five auth forms **inside the chat message stream** instead of in a proper second pane, so there was never a real content-pane for this responsive mechanism to apply to.

**AI Engine's own nav-pane (SPEC-19 §12 step 2.1) is the direct precedent for the left pane too** — a flat menu (there, Patients/Staff/Encounters; here, Register/Login/Forgot Password/Change Password) is already the accepted honest stand-in until Task persistence (§2) justifies a real Task-driven navigator. The entry-menu buttons already built are structurally the same thing, just currently rendered as a chat message instead of a standing column.

## §5.4 — Hospital setup, real LForms, group-at-a-time, driven by Cübo

User pointed out a real, unresolved inconsistency: THREE separate surfaces all capture/edit the same Hospital data with different (sometimes incompatible) mechanics —
1. `HospitalOnboarding.vue`'s drawer — surgical `withGroupFields` writes across 3 groups, custom `AbdmFieldForm` rendering (not real LForms/FHIR).
2. `HospitalOnboardingChat.vue` — the identical 3 groups and save calls, literally copy-pasted (its own header comment: *"not deduplicated... a side-by-side comparison, not a committed replacement"*) — a never-resolved experiment.
3. Designer.vue's "Hospital Profile" card — architecturally different: real LForms, but renders the WHOLE 8-entity Provider document and overwrites it wholesale on save (`extractResponse`), not surgical.

**User's directive, resolving the technical approach**: *"We will use the Provider-entity machinery as it FHIR compliant, using the group fields concept in lhcforms can we capture grouped fields one step at a time from cubo?"* — real LForms rendering (Designer's approach), but scoped to ONE group at a time and sequenced by Cübo (neither AbdmFieldForm's bespoke renderer nor Designer's whole-document overwrite). Built and live-verified — feasible, confirmed rather than assumed.

**New data-layer primitives** (`formsLibrary.js`/`formData.js`, re-exported via `useSystemForms.js`):
- `sliceQuestionnaireGroup(questionnaire, groupLinkId)` — a Questionnaire narrowed to one group's `item`. A single-group Questionnaire is valid FHIR on its own; LhcFormHost needed no changes to render it.
- `sliceRecordGroup(record, groupLinkId)` — the record-side counterpart. **Real bug found live, not assumed**: LForms' own `mergeFHIRDataIntoLForms` threw (`Cannot read properties of null (reading 'dataType')` inside its internal `_processQRItemAndLFormsItem`) when handed a record carrying OTHER groups the sliced Questionnaire has no item for — it does NOT gracefully skip them, contrary to this session's first assumption. Fixed by narrowing the record to match the Questionnaire's own scope.
- `mergeGroupResponseItem(recordData, groupResponseItem)` — merges one real FHIR QuestionnaireResponse group (as `LhcFormHost.extract()` returns for a sliced render) back into the full document, replace-or-append by linkId. Deliberately NOT routed through `withGroupFields`' flat-map API — that would flatten real answer types (`valueCoding`, `valueBoolean`, multi-value) down to `valueString` only, the opposite of "FHIR compliant."

**Real runtime, not a fake sequencer**: `hospitalSetupPlanDefinition.js` — a hand-authored JS mirror of `hospital-setup-workflow-v1.yaml`, verified action-for-action equivalent to what that YAML compiles to. COMPLETE-driven (no `services`), matching the already-tested FIVE_ROOM_PLAN precedent — "done" means the user saved that group's real LForms fields, not an async API call this file would own. `hospitalSetupWorkflow.js` (new Pinia store) wraps it exactly like `entryWorkflow.js` wraps the entry plan — persisted via the same `taskActorSnapshots` collection (real resumability), with a `complete()` that auto-focuses whatever became ready next so Cübo's UI doesn't need its own "what's the next step" logic.

**Cübo wiring**: a new "Set Up In Cübo (step by step)" button in the right pane's Next Best Action tab (hospital_admin/admin_and_health_professional only) starts the flow; the Content tab renders the current step's sliced Questionnaire+record via `LhcFormHost`, with a Save & Continue button that extracts, merges, saves, publishes (matching `HospitalOnboarding.vue`'s own publish-on-save behavior), and advances. `timelineMessages`' audit-log merging (§5.2 item 3) generalized to include `hospitalSetupWorkflow.auditLog` alongside `entryWorkflow.auditLog`, so every real transition shows up in the chat timeline for free.
