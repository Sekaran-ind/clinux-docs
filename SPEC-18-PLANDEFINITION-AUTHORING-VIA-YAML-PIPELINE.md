# Specification 18: PlanDefinition Authoring via the Existing YAML/Questionnaire/Extraction Pipeline

## 1. Objective

Answer `docs/SPEC-16-NOTEBOOKS-AND-TASK-PRIMARY-NAVIGATION.md` §6 step 1's open gap — how `PlanDefinition` actually gets authored — without adopting a new tool or relying on passively parsing existing data-capture YAML (insufficient on its own, §3). Confirm the resulting Definition→Request→Event chain genuinely supports real-world, multi-actor coordination (§5), and validate — with one correction — a proposal to reuse the same mechanism for reference/master-data lists (§6). Nothing here is built yet.

## 2. The mechanism

Author a dedicated `workflow-definition.yaml`, the same `composition:`-block syntax already used everywhere in this codebase, targeting `resourceType: PlanDefinition`/`Task` instead of Organization/PractitionerRole/etc. Compile it through the **existing** `yaml-to-questionnaire.js` pipeline, unmodified — it produces a `Questionnaire` whose items represent workflow concepts (action id/title, `relatedAction` target + relationship, condition). Fill it out as a `QuestionnaireResponse` — the actual authoring act, a person defining their workflow's shape through a form, same as any other room. Run it through `local-extractor.js` — **verified this session (again) to be generic**: it buckets captured answers by whatever `resourceType` appears in each item's `definition` string, with no hardcoding beyond a few additional special-case reference-linking rules for specific types (Organization↔PractitionerRole↔Location). It produces a real `PlanDefinition` resource, using extraction code that already exists, unmodified.

New work, stated precisely, not glossed over: (1) author the `workflow-definition.yaml` content itself; (2) extend the shard graph (the compile-time allowed-FHIR-paths validator) to recognize `PlanDefinition`/`Task` field paths; (3) a constrained, coded field for `condition` — never free text, same rule already established for LGD codes and for Stately's guard functions (SPEC-12 §4.3).

## 3. Comparison to the two approaches this supersedes

- **vs. Stately** (raised last, now retired as the authoring path): no new dependency, one consistent authoring paradigm across the whole system, compile-time validation for free via the shard graph. Honest cost carried forward, not dropped: a form-fill UI is less visually clear for graph-shaped content (branching states/transitions) than a rendered diagram. Mitigation, not dismissal: keep a visualizer — Stately's own import capability, or XState's inspector — as an *optional, derived review layer* over the already-compiled output, not the authoring surface.
- **vs. passively parsing existing data-capture YAML** (the approach before Stately, also superseded): that could only ever produce intra-room structure, because a room's own YAML has no reason to know other rooms exist. A dedicated workflow-definition YAML solves this because its content is deliberately about sequencing, not inferred from something never designed to carry that information.

## 4. Scope boundary

This pipeline produces the `PlanDefinition` resource — Definition tier. It does not touch Task generation, `Task.status` transitions, or the closed loop's `relatedAction` re-evaluation. Those remain exactly as `docs/SPEC-13-FHIR-WORKFLOW-DOCUMENTS-AND-CONFORMANCE.md` §2 already designed, and are still not built — the actual remaining gap after this spec.

## 5. Validating real-world coordination

Confirmed, with one honest caveat. Walking the mechanism end to end against what "real-world coordination" actually requires:

- **Actor-scoping is correct.** `Task.owner` (primary) + `Task.partOf` (supporting), SPEC-13 §4.3, give each real person exactly their own bounded slice of the same `PlanDefinition` instance — a front-desk clerk, a resident, an attending each see only their own Task's bounded context (SPEC-12 §4.2), while the notebook/left-pane navigator (SPEC-16 §5) shows the whole instance's progress so anyone can see what's done or next without needing access to act on it.
- **The handoff signal is real, not hypothetical.** SPEC-13 §2.3's closed loop — Task completes → `relatedAction` re-evaluated → next Task becomes ready → Cübo notifies that Task's owner — rides on the already-shipped, live-verified P2P chat infrastructure (`clinux-p2p-user-chat-feature` memory, tested with two real browsers). This is wiring an already-working notification channel to an already-designed trigger, not inventing new coordination machinery.
- **Task-owner assignment correctly depends on the roster's live state.** The affiliation/roster machines (prior session discussion) — `PractitionerRole`/`OrganizationAffiliation`'s `active` + `period` — determine who's even eligible to be assigned a Task at generation time. Confirms the pieces click together end to end (roster liveness → Task assignment → bounded-context execution → completion → notification → next Task ready), not just pairwise.
- **The honest caveat**: none of this runs yet. This spec makes `PlanDefinition` authorable. The runtime — persisting live Task instances, actually firing status transitions and notifications — is still SPEC-13 §2's unbuilt compiler-and-runtime step. A sound design for coordination is not the same claim as coordination happening today.

## 6. Validating: authoring LGD and other reference lists the same way

Partially yes — worth a precise correction on resource type rather than a flat confirmation, for the same reason getting the resource type right has mattered every other time in this series.

**LGD codes and similar master lists are `ValueSet` content, not `PlanDefinition`/order-set content.** FHIR's actual resource for "the defined set of valid codes a field may take" is `ValueSet`. An "order set" (`PlanDefinition.type = order-set`) is a genuinely different thing — a reusable, selectable *bundle of clinical actions/orders* (e.g., a "Cardiology Consultation" order set bundling the typical actions for that specialty visit) — Workflow-tier content, not Terminology-tier. Modeling "the list of valid Tamil Nadu districts" as a bundle of clinical actions would be structurally wrong, even though both are loosely "curated lists."

**What does hold, and is the useful part of the idea**: the *mechanism* — author via YAML through the existing compiler, fill via Questionnaire, extract via `local-extractor.js` — is genuinely resource-type-agnostic (§2), so it works for `ValueSet` exactly as it works for `PlanDefinition`. A `reference-list-definition.yaml` targeting `resourceType: ValueSet` (fields: code, display, system) run through the identical pipeline produces a real `ValueSet`. This is the concrete path to finally replacing SPEC-14 §7's placeholder LGD demo codes (`TN-DEMO` etc.) with a properly-modeled reference list — still needs the real ABDM master data populated as a separate, later step, but now with the correct resource shape to receive it instead of a hand-coded placeholder array in `abdmSchema.js`.

**Order sets do have a genuine, correct use here — just not for reference lists.** SPEC-13 §4.1's specialty-templated Consultation actions (a Cardiology-specific bundle of typical sections/actions) are a real, correct fit for `PlanDefinition.type = order-set`. Worth keeping as a distinct, valid use of this same authoring mechanism, alongside plain `PlanDefinition` (protocol/workflow-definition type, for room sequencing) and `ValueSet` (for reference lists) — three resource types, one shared authoring pipeline, not one resource type stretched to cover all three jobs.

   - `yaml-to-questionnaire.js` compiles a `type: "group"` field into a real nested FHIR group item, complete with its own `definition` string (so an extractor knows exactly which array-typed FHIR path it represents, not just its leaf children) — recursive, any depth. Also picked up **group-level `skipLogic` → `enableWhen`** for free while restructuring this (sections, not just fields, can now be conditionally shown/hidden — the other half of "LHC-Forms supports conditions to display or hide sections or elements").

Confirmed end to end against the real file: compiles with zero errors, extracts a realistic response correctly — the dependency-free room stays untouched, the dependent room gets its own correctly-nested `relatedAction`, zero warnings. 4 tests in `workflow-definition-draft.test.js`, 2 new compiler tests in `yaml-to-questionnaire.test.js`, 1 new extractor test in `local-extractor.test.js`.
